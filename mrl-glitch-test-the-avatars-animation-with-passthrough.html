Before creating the project

  1. Open Meta Quest Developer Hub (MQDH)

    • Confirm the Quest shows as connected (USB).
    • If a prompt appears inside the headset (“Allow USB debugging?”), accept it.

  2. Unity Hub → New project

    • Template: 3D (URP) (or “3D Core” if URP is not available; I prefer URP because it’s usually the most stable path with XR).
    • Inside SRP there are two main pipelines:
      • URP (Universal Render Pipeline) → lightweight, good for VR/MR/mobile (Quest fits here)
      • HDRP (High Definition Render Pipeline) → heavy, aimed at high-end visuals (not what you want for Quest)
    • Suggested name: MRLGlitch_Passthrough_FBX_Test
    • Location: a short path without weird spaces (to avoid Android build headaches).

There isn’t an “official Unity Hub template” that ships with passthrough ready. The real shortcut is:
Create 3D URP + import Meta XR SDK + run the Project Setup Tool + add Passthrough Building Blocks.

After creating the project (the short path to Passthrough)

A) Switch to Android (Unity 6 = Build Profiles)

  1. Go to File → Build Profiles
  2. On the left panel, select Android
  3. Click Switch Platform (or Switch / Activate, depending on what appears)
  4. Wait for Unity to finish switching (asset reimport may happen)

B) Enable XR (OpenXR) — and validate the build for Quest 3 (Unity 6)

B1) Enable OpenXR on Android

  1. Go to Edit → Project Settings → XR Plug-in Management
  2. Select the Android tab
  3. Check OpenXR

B2) Configure OpenXR (interaction profile + features)

  1. Still in Project Settings, open OpenXR (menu on the left column)

  2. Under Enabled Interaction Profiles, ensure at least 1 profile is enabled

    • Example: Meta Quest Touch Pro Controller Profile (or equivalent)

  3. Under OpenXR Feature Groups, make sure the Meta XR group is enabled/selected (when available)

B3) Confirm essential Player Settings (Android/Quest compatibility)

  1. Go to Edit → Project Settings → Player

  2. Tab Android

  3. Open Other Settings and confirm:

    • Scripting Backend = IL2CPP
    • Target Architectures: ARM64 checked (ARMv7 unchecked, if it appears)
    • (if requested by validation) Minimum API Level / Target API Level: keep what Unity/OpenXR suggests

B4) Make sure nothing “Required” is still pending

  1. Go to Edit → Project Settings → Project Validation
  2. Confirm there are no Required fix (red) items related to OpenXR/Android

Note: if you see “Required fixes” in the status bar referencing Project Setup Tool, that’s usually from Meta XR (step C), not from OpenXR.

C) Import and configure the Meta XR SDK (for Passthrough on Quest 3)

C1) Import Meta XR All-in-One SDK (the correct way on Unity 6)

  1. Open Window → Package Manager
  2. In the top-left of Package Manager, change the Source to My Assets
    (not “Unity Registry” — you won’t find Meta’s SDK there)
  3. Search for Meta XR All-in-One SDK
  4. Click Download (if it isn’t downloaded yet)
  5. Click Import
  6. In the import window, keep the defaults and confirm Import

If Meta XR All-in-One SDK doesn’t show up under My Assets:

  • It means the asset hasn’t been added to your Unity/Asset Store account yet.
  • The correct action is to add it to your account, and then it will appear under “My Assets” in Unity.

C2) Run Meta XR Project Setup Tool (apply Recommended fixes and resolve anything required)

  1. Open the Meta XR Tools panel:

    • Top menu: Meta → Meta XR Tools (or click “Welcome to Meta XR SDK” if it already opened)

  2. Click Project Setup Tool

  3. On the Project Setup Tool screen:

    • Check the status at the top. In your case it looks like:
      “There are X outstanding Recommended fixes.”
    • Under Recommended Items, click Apply All

  4. Under Manually Fixable Items, handle like this (for a passthrough + FBX local test):

    • Complete a Data Use Checkup…
      • For local testing (not store release), you can ignore.
      • If the tool allows it, use Mark as Fixed just to clear the warning.
    • Set up the application ID and the package name…
      • Package name: worth setting now to avoid build confusion on the Quest.
        Example: com.cieglitch.mrlglitch.passthroughtest
      • Application ID (Meta Platform / entitlement): if you are not using Platform SDK now, you can ignore (or “Mark as Fixed” if allowed)

  5. (Optional, but useful) If the Console shows something like:
    “at least the Oculus Touch Interaction Profile should be included…”
    that’s from OpenXR (not the Meta Setup Tool). Fix it here:

    • Edit → Project Settings → OpenXR
    • Under Enabled Interaction Profiles, also add Oculus Touch Controller Interaction Profile (or equivalent)

Expected result: after Apply All, warnings drop a lot and the project is in a Quest-friendly configuration (performance + compatibility).

D) Add Passthrough to the scene

  • Open Meta XR Tools
  • Click Building Blocks
  • Add the minimum blocks:
    • Camera Rig (or the equivalent Meta rig/camera block)
    • Passthrough
  • Make sure you don’t have two cameras:
    • If your scene still has the default URP Main Camera, either:
      • disable it (GameObject checkbox), or delete it
    • The Meta rig will provide the camera XR needs.
  • Ensure your 3D content can be visible over passthrough:
    • Keep a Directional Light (or a simple light) in the scene — without light, FBX meshes can look dark/invisible even if passthrough works.

Headset test

  • File → Build Profiles → Android → Build And Run
    • macOS will open a Build Android window asking where to save the APK.
    • In Save As: type something like MRLGlitch_Passthrough_Test.apk
    • Save outside the project folder, e.g. a “Builds” folder
  • Click Save
    • If Unity warns:
      “Android SDK is missing required platform API level(s): 32”
      click Update Android SDK to install Android SDK Platform 32
      (this is a SDK component and usually only needs to be installed once per machine).
  • After the build finishes and the APK is installed:
    • On Quest: Library → Unknown Sources → open your app
    • You should see the real world (passthrough) + your Unity scene on top.

E) Import FBX + autoplay loop + WorldRoot (world-anchored)

E1) Import the FBXs

  • Put the files in Assets/FBX/ (e.g. 01_Anim.fbx ... 05_Anim.fbx)

E2) Set each FBX animation to loop

For each FBX (01_Anim.fbx, 02_Anim.fbx, etc.):

  1. Click the FBX in the Project (Assets)

  2. In the Inspector:

    • Animation tab
    • Check Import Animations (if unchecked)
    • In Clips (or the listed clip), enable:
      • Loop Time
      • (optional) Loop Pose

  3. Click Apply

E3) (Important) Rig = Generic (to preserve transforms/scale from “transform baked”)

Since the FBXs came with transform baked (Unreal → Unity pipeline), it’s safer to keep the rig as Generic.

  1. In the Project, select the asset 01_Anim.fbx (not 01_Anim in the Hierarchy)
  2. In the Inspector, open the Rig tab
  3. Set Animation Type to Generic
  4. Click Apply

If you select the object in the Hierarchy, you won’t see Model/Rig/Animation tabs — those tabs only appear when selecting the FBX file in the Project.

E4) Create a WorldRoot (world anchor reference)

  1. In the Hierarchy: GameObject → Create Empty

  2. Rename it to: WorldRoot

  3. With WorldRoot selected, in Inspector → Transform:

    • Position: X = 0, Y = 0, Z = 0
    • Rotation: 0, 0, 0
    • Scale: 1, 1, 1

This keeps content “fixed in the world” (not attached to the camera). In a first test, it’s anchored to the reference frame created when the app starts.

E5) Put one FBX into the scene as a child of WorldRoot

  1. Drag 01_Anim.fbx from Project into the Hierarchy

  2. Drag it to become a child of WorldRoot (indented under it)

  3. Keep the FBX Transform clean (local to WorldRoot):

    • Position: 0,0,0
    • Rotation: 0,0,0
    • Scale: 1,1,1

E6) Autoplay — Animator Controller

If pressing Play does not make the FBX animate automatically:

  1. In Project: Assets → Create → Animator Controller

    • Name: AC_01_Anim

  2. Double click the controller to open the Animator window

  3. Expand the FBX asset (small arrow next to the file) and find the Animation Clip

  4. Drag the clip into the Animator window

  5. Ensure it becomes the Default State (orange)

  6. Select the FBX GameObject in the Hierarchy and in Inspector:

    • Add an Animator component (if it doesn’t exist)
    • In Controller, assign AC_01_Anim

✅ Result: when the app starts, the animation plays automatically and (because of Loop Time) loops.

E7) Quick sanity check in the Editor

  • Press Play
  • Confirm:
    • the FBX is visible
    • the animation runs in a loop

F) Quest test (passthrough + FBX in the world)

  • File → Build Profiles → Android → Build And Run
    • On Quest: Library → Unknown Sources → open the app

You should see:

  • passthrough
  • the avatar animating in loop, fixed in the world

F1) Fix: avatar “disappears” when you turn/move sideways (culling / bounds)

Symptom: the avatar disappears when you move right/left, like there’s a viewing limit.

Common cause: Unity culls skinned meshes based on the Skinned Mesh Renderer bounds. Some animated FBXs import bounds that are too small/wrong.

✅ Fix (worked in our case):

  1. In the Hierarchy, expand 01_Anim (arrow ▶) and select the child that contains the mesh (e.g. Body, Mesh, etc.)
  2. In the Inspector, find Skinned Mesh Renderer
  3. Enable: ✅ Update When Offscreen

Note: this component usually is NOT on the 01_Anim root (root often has only Transform + Animator). You must click a child that holds the mesh.

F2) (Best practice) Avoid “weird offset”: keep the FBX clean, fix axis on WorldRoot, offset on AnimOffset

  • Keep 01_Anim with a clean local Transform:
    • Position 0,0,0
    • Rotation 0,0,0
    • Scale 1,1,1
  • Use WorldRoot only for axis/orientation correction:
    • Rotation X = -90 (axis fix, if needed)
  • Create a child under WorldRoot named AnimOffset, and use it to place the avatar in space:
    • Adjust AnimOffset.Position (example: Y = -2 in your case)

Why did Y = -2 work (instead of pushing on Z)?
With WorldRoot.X = -90, the local axes effectively rotate, so “moving on Y” at the AnimOffset level can behave like “moving forward/back” in world space (depending on your axis fix + imported rig orientation).
